# Reproducibility, run commands, integrity, and validation

## 1. Repository and environment

Run commands from the repository root. An existing intended Linux GPU
installation uses Python 3.10, the saved research dependency environment,
Flower/Ray and CUDA; do **not** install a local CPU-only set of packages over
that machine. For isolated development, `python -m pip install -e .` is
conventional; inspect `pyproject.toml` and `requirements.txt` first.

```bash
cd /path/to/bayesfl
export PYTHONPATH="$PWD/src${PYTHONPATH:+:$PYTHONPATH}"
PY=python     # replace with the EXACT approved experiment interpreter
"$PY" -m pytest -q tests/wireless
"$PY" -m pytest -q
```

A skipped optional Flower, Bayesian-Torch, Ray or CUDA test is **not** a passed
system integration gate. The records at `validation/` describe the historical
release's checks. New checks must be reported separately with exact command,
exit code, test count and environment.

## 2. Immutable experiments and partition identities

For every run save `source_config.yaml`, **resolved** `resolved_config.yaml`,
partition-content metadata/hashes, environment and run summary. The same
configuration text does not certify the same partition NPZ; the runner checks
partition-content SHA-256 on load/resume. Deterministic client IDs and round
seeds keep local SGD, score masks and channel randomness separated. Do not
change seed/partition, optimizer, clipping, schedule or model while claiming to
resume an existing trajectory.

Canonical first-submission profiles are in `docs/EXPERIMENT_REGISTRY.json`,
with exact results under existing `outputs/run*/` directories in the full
archive. Historical `scripts/configs/` YAMLs and `scripts/queues/` are kept
for provenance, not autorun. Use explicit config names; never select a
“latest” file by a wildcard without checking its manifest.

## 3. Running existing CLI paths (examples, not authorization for long training)

Legacy run (creates its own new run directory):

```bash
"$PY" -m bayesfl.main --config scripts/configs/fola_mnist.yaml
```

Actual paper study configurations should be selected from their saved
profiles/registry, not from this generic default example. For the wireless
local **synthetic** three-round smoke:

```bash
"$PY" scripts/smoke_wireless_offline.py \
  --output-dir "outputs/smoke_wireless_unique_$(date +%Y%m%d_%H%M%S)" \
  --rounds 3
```

For reviewed wireless studies, `scripts/prepare_wireless_study.py` clones
locked learning configs while recording wireless scenario, inheritance
hashes and queue definitions. `scripts/_run_wireless_queue.sh` accepts a
separate wireless command grammar; the legacy `_run_gpu_queue.sh` uses
fixed-byte budgets and cannot be substituted. Always inspect the generated
configuration, partition availability, GPU occupancy and explicit queue
contents before a launch. `scripts/summarize_wireless_results.py` and
`scripts/plot_joint_cifar_sensitivity_v1.py` read results without retraining.

To check a saved legacy first-submission set:

```bash
"$PY" docs/tools/export_handoff.py --check
```

This expects the full primary output directories; a source-only ZIP
correctly lacks those files. A source-only tree cannot reproduce endpoints
without the original data and saved results.

## 4. Outputs versus reports

Raw run evidence belongs in `outputs/run_.../`: evaluator metrics,
client-round CSVs, exact allocation JSON, protocol, channel trace,
`wireless/events.jsonl`, checkpoint arrays and `wireless_resume` state.
A report under `reports/` is generated by *reading* a completed run and
copies **selected** metrics/config/hashes, not checkpoint arrays. See
[`reports/README.md`](../reports/README.md) for the exact CLI, schema,
report template and strict/records-only distinction.

Do not “clean” `outputs/` to make a small ZIP. The source-only distribution
excludes outputs intentionally; the complete release retains them **at their
existing paths**. Never overwrite or rename original completed trajectories.

## 5. Checkpoint and resume integrity

Wireless resume is `outputs/<run>/wireless_resume/` and validates round,
layout/snapshot, configuration fingerprint, partition/trace content, array
checksum, tracked CSV hashes and event-ledger byte checksum. Only a larger
**total round cap** and/or **total modeled-time cap** may be permitted.
No mid-round retry is misrepresented as a clean evaluated-round resume;
no legacy checkpoint may be imported as wireless v2 state.

Original archived state JSON/event ledgers can acquire different *raw bytes*
when text utilities convert LF to CRLF. Raw SHA-256 then disagrees even if
parsed JSON and model arrays look plausible. Do **not** convert and rewrite
checksums as an automatic “repair.” The research report tool has an explicit
`--records-only` mode that reads metric accounting but labels state integrity
unverified. Only the original verified checkpoint source should authorize
resume.

## 6. Scientific acceptance checklist

For a documentation/workflow-only refactor: match hashes of learner,
models, partitions, original reducer, KL/codec and wireless allocator;
run focused tests then broad pytest; verify sample-weighted discarded KL,
packet bytes (including dense switch), omitted-prior fill, and fixed slots.
No full 150-round retrain is necessary for a non-scientific documentation
move. For *new algorithm changes*, add small numerical/frozen-round tests,
a new run identity and a planned learning comparison before expensive runs.

Legacy models remain controlled by the selected YAMLs; wireless examples
are not physically calibrated. Do not infer accuracy convergence from a
synthetic smoke or global optimality from the allocator's numerical gap.
